## Report Phaseとの境界

- Workflow ContextのReport DirectoryはPhase 1では読み取り専用です。
- `plan.md`などのoutput contract対象ファイルを直接作成、変更、移動、削除しないでください。
- 計画の「作成」「出力」は、Phase 1の最終回答として計画内容を返す意味です。
- レポートファイルの保存は、Workflowの`output_contracts`とTAKTのReport Phaseが担当します。

## docs-only 計画手順

1. タスク指示書のチェックリストを全件読み、各項目を安定したIDで列挙してください。
2. 各チェックリスト項目について、次の対応表を作ってください。
   - チェックリスト項目
   - 記載先ファイル
   - 記載位置（`file:line`、trait名、型名、メソッド名など）
   - 記載内容の正本
   - 完了確認方法
3. 記載内容の正本を、実際のテスト・実装・ADR・公開契約から特定してください。
   - テストが契約の正本で、docがその文書化であるタスクでは、その従属関係を明記してください。
   - 正本を推測しないでください。確認できない場合は情報不足として扱ってください。
4. **テスト作成を計画しないでください。**
   - docs-onlyタスクでは、ドキュメント本文や文言を固定するためのテストを新設しません。
   - 既存テストは記載内容の正本・挙動確認のために参照または実行できます。
5. 変更予定をdocs-onlyの範囲へ限定してください。
   - doc comment (`///`, `//!`)
   - READMEや既存ドキュメント
   - その他タスクで明示された文書ファイル
6. シグネチャ、実装、テスト、設定など、実行時挙動を変える修正が必要だと判明した場合は、
   docs-onlyタスクとして続行しないでください。
   - 計画結果に必要なコード変更と理由を明記してください。
   - コード側Issue/タスクへの分離を提案し、ワークフローはABORT判定にしてください。
7. 最終計画には「チェックリスト項目 → 記載箇所 → 正本 → 検証」の対応表を必ず含めてください。

docs-onlyの目的は、既存契約を正確に文書化することです。新しい仕様をdoc側から作らないでください。
