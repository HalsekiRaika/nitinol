# Rust Docs-Only Policy

## 適用範囲

- `default-rust-docs`のplan / write / review / fixで、docs-onlyの境界を共有するためのPolicyです。
- タスク指示書、既存テスト、実装、ADR、公開契約を正本とし、doc側から新しい挙動契約を作りません。

## Docs-only境界

許可する変更:
- Rust doc comment (`///`)
- module / crate doc (`//!`)
- READMEおよびタスクが明示した文書ファイル

禁止する変更:
- プロダクションコードの挙動
- 公開・非公開シグネチャ
- 実装ロジック
- テストコード
- Cargo設定、feature、依存関係
- docs-onlyタスクのためだけの補助APIやコード分岐

docsだけでは完了できず挙動変更が必要な場合は、無理に修正せずコード側Issue/タスクへ分離してください。

## 正本との整合

- docへ書く契約・境界・失敗条件は、記載前にテスト・実装・ADR・公開契約で確認してください。
- テストが正本である場合、docはその内容に従属します。
- 実装が保証しない性質を「保証する」「必ず」「常に」等の契約として追加しないでください。
- 正本間に矛盾がある場合は、docs側で勝手に解釈を固定せず差し戻してください。

## テスト

- docs-onlyタスクで新しいテストを作成しないでください。
- ドキュメント本文、文言、章立てを固定するsnapshot/string test等を作成しないでください。
- 既存テストの参照・実行は、記載内容の正本確認と回帰確認のために許可します。

## Rustdoc

- Rust APIへの参照は、可能な限りintra-doc linkを使用してください。
- リンク切れ、rustdoc warning、doc build failureを残さないでください。
- doc例が実行可能コードとして扱われる場合も、タスク範囲を越えて実装やテストを変更して通過させないでください。

## レビュー観点

docs-onlyレビューでblocking findingとして許可するのはD1〜D4だけです。

- D1: タスクチェックリストの記載漏れ・内容欠落
- D2: 正本（テスト・実装・ADR・公開契約）との矛盾
- D3: doc build、リンク、quality gate等の機械的問題
- D4: docs以外の挙動変更の混入

次はblocking findingとして禁止します。

- 文体、語調、表現の好み
- 一般的な章立て・構成改善
- チェックリスト外の追加説明
- スコープ外の改善提案

「より良くできる」だけでは`needs_fix`にしません。

## 修正

- findingは現在のファイルで再確認してから修正してください。
- D1〜D4に該当しないfindingは対象外として扱い、修正しません。
- レビューを満たすためだけの挙動変更、テスト追加、過剰な説明追加を行わないでください。
